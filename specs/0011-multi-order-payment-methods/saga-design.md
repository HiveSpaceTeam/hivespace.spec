# Saga Design: Multi-Order Checkout Payment

- **Feature**: `0011-multi-order-payment-methods`
- **Date**: 2026-07-11
- **Owner service**: OrderService
- **Saga type**: MassTransit StateMachine
- **Status**: Draft

## Purpose

Update the existing checkout saga so one checkout-level PaymentService payment covers every order generated by the checkout and can contain multiple payment attempts. The saga remains owned by OrderService because it coordinates order creation, inventory reservation, current-attempt payment outcome handling, coupon commits, cart clearing, compensation, and fulfillment handoff.

## Trigger Conditions

| Trigger | Source | Message/API | Notes |
| --- | --- | --- | --- |
| Checkout request | Buyer app | `POST /api/v1/orders/checkout` | Request includes canonical payment method code from PaymentService metadata. |

## Participants

| Participant | Responsibility | Messages handled |
| --- | --- | --- |
| OrderService | Own checkout saga, create orders, generate order codes, apply payment outcome to orders, compensate on failure. | `CheckoutInitiated`, `CreateOrder`, `MarkOrderAsPaid`, `MarkOrderAsCOD`, `CancelOrder`, `CommitCouponUsage` |
| PaymentService | Create one checkout-level payment, own reference number, create COD/VNPay attempts, publish current-attempt payment outcomes. | `InitiatePayment`, `PaymentInitiatedIntegrationEvent`, `PaymentSucceededIntegrationEvent`, `PaymentFailedIntegrationEvent`, `PaymentInitiationFailedIntegrationEvent` |
| CatalogService | Reserve/release/confirm inventory unchanged. | `ReserveInventory`, `ReleaseInventory`, `ConfirmInventory` |
| NotificationService | Fulfillment notifications unchanged. | Existing fulfillment notification messages |

## State Machine

```text
Initial
  -> CreatingOrders
  -> ReservingInventory
  -> InitiatingCheckoutPayment
  -> WaitingForPaymentOutcome
  -> RetryingPayment (optional while eligible)
  -> ApplyingPaymentOutcome
  -> CommittingCouponUsage
  -> HandingOffToFulfillment
  -> Completed

COD path:
  -> InitiatingCheckoutPayment
  -> ApplyingCodOutcome
  -> CommittingCouponUsage
  -> HandingOffToFulfillment
  -> Completed

Failure:
  -> Compensating
  -> Failed
```

## Messages

### Commands Published

| Command | Target | Purpose | Success event | Failure event |
| --- | --- | --- | --- | --- |
| `ReserveInventory` | CatalogService | Reserve selected SKU inventory. | `InventoryReservedIntegrationEvent` | `InventoryReservationFailedIntegrationEvent` |
| `InitiatePayment` | PaymentService | Create one payment and attempt for all generated orders. | `PaymentInitiatedIntegrationEvent` | `PaymentInitiationFailedIntegrationEvent` |
| `ReleaseInventory` | CatalogService | Release inventory during compensation. | `InventoryReleasedIntegrationEvent` | Existing retry/dead-letter behavior |
| `CommitCouponUsage` | OrderService | Commit coupon usage after payment/COD success. | `CouponUsageCommittedIntegrationEvent` | `CommitCouponUsageFailedIntegrationEvent` |

### Events Consumed

| Event | Source | Effect |
| --- | --- | --- |
| `OrderCreatedIntegrationEvent` | OrderService | Store generated order IDs/codes and totals in saga state. |
| `InventoryReservedIntegrationEvent` | CatalogService | Continue to payment initiation. |
| `PaymentInitiatedIntegrationEvent` | PaymentService | Store shared payment ID/reference, current attempt identity, and redirect URL if VNPay. COD can continue to COD marking. |
| `PaymentSucceededIntegrationEvent` | PaymentService | Mark every linked order paid exactly once when attempt identity matches current saga state. |
| `PaymentFailedIntegrationEvent` | PaymentService | Fail, wait for retry, or compensate every linked order that depends on the shared payment when attempt identity matches current saga state. |
| `PaymentInitiationFailedIntegrationEvent` | PaymentService | Compensate order/inventory state. |

## Compensation

| Failed step | Compensation action | Owner | Notes |
| --- | --- | --- | --- |
| Payment initiation fails | Cancel generated orders and release inventory if reserved. | OrderService/CatalogService | Preserve observable failure reason. |
| VNPay payment fails/expires | Keep linked orders unpaid and allow retry while eligible; compensate only after retry is abandoned or eligibility is lost. | OrderService | Apply only for current attempt. |
| Stale older-attempt callback arrives | Record diagnostics and ignore order transitions. | PaymentService/OrderService | Older attempt outcomes must not override newer attempt or succeeded payment state. |
| Coupon commit fails after payment/COD success | Surface failure through saga retry/dead-letter; do not silently swallow. | OrderService | Existing reliability rules apply. |

## Timeouts And Retries

| Step/state | Timeout | Retry policy | Timeout event |
| --- | --- | --- | --- |
| Payment initiation request | Existing MassTransit request timeout | Existing retry/dead-letter policy | `SagaStepExpiredIntegrationEvent` if configured for request expiry |
| VNPay buyer completion | Existing payment expiry window, currently documented as 15 minutes | Gateway callbacks idempotent; saga handles final payment event once | `PaymentTimeoutIntegrationEvent` / `PaymentFailedIntegrationEvent` |
| Buyer payment retry | Allowed after failed/expired/cancelled attempt while orders remain eligible | New attempt uses PaymentService idempotency key; stale callbacks ignored by attempt identity | N/A |

## Idempotency And Consistency

- Payment creation uses PaymentService idempotency key and validates the repeated request shape.
- Payment retry creates a new child attempt under the same `ReferenceNo`; repeated retry requests with the same idempotency key return the same attempt.
- `ReferenceNo` is public and must not be reused as the idempotency key.
- PaymentService publishes current-attempt outcome events once per effective state transition through the outbox.
- OrderService validates event correlation, linked order set, and attempt identity against saga state.
- Order payment/COD marking is idempotent per order and guarded by saga state.

## Observability

- Correlation ID: checkout saga `CorrelationId`, included in payment commands/events.
- Required logs: payment initiation request shape, generated payment reference, state transitions, duplicate gateway callback handling, linked-order outcome application, compensation steps.
- Health/diagnostics: MassTransit inbox/outbox, payment callback logs, dead-letter queues, PaymentService gateway diagnostics.
